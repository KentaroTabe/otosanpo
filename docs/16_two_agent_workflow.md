# 16. 2 者で作る手順(Claude Code と Codex・2026-09-08 開始)

**片方が実装し、実装しなかった方が確認とテストを行う。** 利用者の指示
(2026-09-08)で始めた運用。ここに手順と道具を置く。

## なぜこうするか

1 者で書いて 1 者で確かめると、**同じ思い込みが実装と検証の両方に入る**。
このプロジェクトでは実際に踏んだ:

- 語を決め打ちで grep して「提案 0 件」と誤報告した(実際は鳴っていた)
- 判断待ちの音の値を Android の APK にだけ焼き込み、配布版と違う音になった
- docs/13 が「壊れた方位が音に出る経路が無い」と書いているのに、
  コードはそれを保証していなかった(2026-09-08 に Codex の指摘で判明)

いずれも「書いた本人が確かめた」ために通り抜けている。
**検証役に実装役の言い分を渡さない**のが、この運用の要点。

## 4 段

```
段 1 合議   課題を書いて往復する。終わりに「受け入れ条件」を確定させる
段 2 実装   実装役が枝を切り、実装 + テストを書く。scripts/test.sh 全緑まで
段 3 検証   検証役は「受け入れ条件」と「diff」だけを見て、条件ごとに合否を出す
段 4 決着   指摘を直す or 理由をつけて反論する。決着したら PR。結論を docs へ
```

### 段 1 合議 — 出口は「受け入れ条件」

議論の出口を**検収できる文**にする。「〜を改善する」ではなく
「〜のとき〜になる」の形。これが無いと段 3 が感想文になる。

```
scripts/ask_codex.sh codex-exchange/01-design.md            # 新しい会話
scripts/ask_codex.sh codex-exchange/02-design.md --resume   # 続き
```

- 生ログは `codex-exchange/`(**gitignore 対象**)。決まったことだけ docs へ書き写す
- お題には**読むべきファイルのパスを書く**。相手もこのリポジトリを読める
- **相手の指摘は鵜呑みにしない。** 自分でコードを開いて裏を取ってから同意する
  (初回、3 件の指摘はすべて成立したが、確かめずに同意すれば運任せだった)

### 段 2 実装

- 枝は `develop` から生やす(README のブランチ運用に従う)
- **受け入れ条件に無いことをしない。** ついでのリファクタリングは別の案件にする
- テストは実装と同じコミットに入れる(CLAUDE.md)

### 段 3 検証 — 実装役の説明を渡さない

```
scripts/handoff.sh <案件名> <基準リビジョン>       # 検証依頼を組み立てる
scripts/ask_codex.sh codex-exchange/<案件名>-check.md --resume
```

`handoff.sh` が渡すのは **受け入れ条件と diff だけ**。実装役のコミットメッセージも
言い訳も入れない。検証役の必須項目:

1. 受け入れ条件を 1 つずつ「満たす / 満たさない / 判定不能」で判定する
2. **テストが弱められていないか**(緩和・skip・期待値の書き換え・削除)。
   CLAUDE.md の明示的な禁止事項であり、検証役の第一の仕事
3. 受け入れ条件に無い変更が混ざっていないか
4. 規約違反(数値のハードコード・レイヤの依存方向・Core の import)
5. **足りないテストを入力と期待値の形で挙げる**(「増やすべき」では受け取らない)。
   挙がったものは実装役が書いて走らせ、結果を返す

### テストは検証役に実行させない(2026-09-08 利用者判断)

Codex にサンドボックス内で `scripts/test.sh` を走らせて確かめた結果、
**CoreSimulator が動かない**(`simdiskimaged` への接続が塞がれ
`Unable to discover any Simulator runtimes`)。実行しても環境由来の失敗しか出ない。

サンドボックスを外せば動くが、**外さない**というのが利用者の判断。したがって:

- 検証役は**テストを実行しない**。読むのは diff と受け入れ条件だけ
- 足りないテストは**入力と期待値の形**で挙げ、実装役が書いて走らせる
- 「緑のはず」と推測で書かせない。実行結果は実装役の報告が唯一の出所になるので、
  **テストのコード自体が diff に出ている**ことが担保になる(だから項目 2 が重い)

### 段 4 決着

- 指摘は直すか、**理由をつけて反論する**。黙って無視しない
- 「利用者が決めるべき」と判定が割れた項目は、実装せずに判断待ちとして上げる
- 決着したら PR。**なぜそう決めたか**を docs の該当ファイルへ書き写す

**案件ごとに交代する。** 同じ側が実装し続けると、検証役が実装の癖に慣れて
指摘が鈍る。

## 道具

| | |
|---|---|
| `scripts/ask_codex.sh <お題> [--resume] [--write]` | お題を Codex へ送り、返答を `<お題>.reply.md` に受ける |
| `scripts/handoff.sh <案件名> <基準>` | 受け入れ条件 + diff を組み立てて検証役へ渡す |
| `codex-exchange/` | 往復の生ログ。gitignore 対象 |

Codex の実体は ChatGPT.app 同梱の CLI
(`/Applications/ChatGPT.app/Contents/Resources/codex`)。PATH に `codex` があれば
そちらを使う。会話の続きは `codex exec resume --last`(作業ディレクトリで絞られる)。

## 分かっている限界

- **往復 1 回に 10〜15 分かかる。** 段 1 を 2〜3 回で終える書き方をする
  (論点を並べ、同意する項目は「同意」で返してもらう)
- 生ログは長い。**読み返す価値があるのは結論だけ**なのでコミットしない
- 検証役が見るのは diff であって、動いているアプリではない。
  **実機の挙動は依然として散歩でしか確かめられない**
