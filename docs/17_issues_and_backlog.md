# 17. 課題の整理と、後で実装するもの(2026-10-26)

2026-10-25 のログ(ポケットに入れて徒歩で移動・2.7 km・37 分)を読んだ結果と、
そのとき棚卸しした技術的な課題を、利用者の判定に沿って整理したもの。

番号は 2 系統ある。**L = このログで見つかったもの、T = 技術的な課題(既存の一覧)**。

## L: 2026-10-25 のログで見つかったもの

| | 見つかったもの | 判定 |
|---|---|---|
| L1 | 自宅が 9/18 の名古屋のまま残り、出発点から 20.5 km 離れていた | **課題。本当の課題は「現在地以外を自宅として登録できない」こと**(利用者判定) |
| L2 | 開始 0.09 秒で時間到来 | 課題ではない。散歩時間を設定しなかっただけ(利用者判定) |
| L3 | 開始 2.9 秒でうなずきを検出 | 課題ではない。**うなずいた**(利用者判定)。検出器は正しく動いた |
| L4 | 経路の場が作れず直線に落ちたが、ログに理由が無い | **課題(開発側の判断・下記)** |
| L5 | 音楽スポットに一度も近づかず、37 分間下限音量 | 課題ではない。音楽スポットを主とした散歩ではない(利用者判定) |

### L4 の判断: 課題とする(ただし挙動ではなく記録の課題)

**単発ではなく「失敗・劣化を黙って捨てる」箇所の 1 つ。** 同じログで 2 箇所、
理由が判定できなかった。

| 箇所 | 起きたこと | 黙っている所 |
|---|---|---|
| 経路の場 | ビーコンが直線に落ちた。**地図が無かったのか、自宅が地図の外だったのかも分からない** | `buildRouteField` の `guard let graph, let h = home, graph.map.covers(h) else { return }` |
| 店の記録 | 0 件。**店が無かったのか、取得に失敗したのか分からない** | `ShopHistoryService.finishPending` の `catch { ... return [] }` |

利用者から見ても劣化は起きている(案内が街区を突っ切る直線になる / 発見 MAP が空になる)のに、
**画面にもログにも理由が出ない**。直すのは記録の行を足すだけで、挙動は変えない。

なお今回の散歩に限れば、L1 が直っていれば経路の場は作れていた**可能性が高い**
(本当の自宅は出発点から 2.3 km で、散歩開始時に取るタイル 5 km 圏に入る)。
ただしタイルが取れていたかはログから確かめられない(未確認)。

### B3: 家へ向かう移動に寄り道を混ぜる

いまのアプリは「家を出て、ぶらつき、家へ帰る」を前提にしている。**出先から家へ歩く**と、
帰宅推定が散歩時間を超えているので出発した瞬間に時間到来になり、散策の部分が無くなる。

ここに別の体験がある — **「家に着けばいいが、急がないので面白い道を通してほしい」**。
帰路そのものに分岐の提案を混ぜる形で、既存の部品(経路の場・分岐の提案・帰宅予算)が
そのまま使える見込み。**「あって良い」ので後で実装するリストへ置く(2026-10-26 利用者判断)。
作るかの最終判断と設計はこれから。**

## 既存の仕組みの課題(T1・T3・T6・T7)— 構造

### どの層の課題か

```
 入力(推定)              判断              出力(提示)        説明
 ─────────────            ─────            ──────────        ─────
 位置 → 経路の追跡  T1     予算・提案         音の定位  T3       画面・文書  T7
 頭   → ジェスチャ  T6
```

| | 層 | 欠陥の形 | 原因の確度 | 歩かずに測れるか | 新しい仕組みとの絡み |
|---|---|---|---|---|---|
| T1 | 入力(位置) | 推定が**前回を見ない** | 高い(コードで特定・再生で再現) | **測れる**(再生) | なし |
| T6 | 入力(頭) | 判別が**振幅だけ** | 高い(振幅で分離できないと実測) | **測れる**(影検出が毎回残る) | T2 と入力源が同じ |
| T3 | 出力 | **伝える経路そのものが無い** | 確定(2026-08-18 実測) | 測れない(聴くしかない) | **T2・T5 次第** |
| T7 | 説明 | 実装と記述の**不一致** | 確定 | 不要 | なし |

### 見えてくる構造

**1. T1 と T6 は同じ形の欠陥。** どちらも「雑音の多い連続量から、文脈を持たずに
毎回離散的な判断を下す」。

| | 雑音の多い入力 | 文脈なしの判断 | 結果 |
|---|---|---|---|
| T1 | GPS の位置(水平精度 平均 13 m) | 毎回いちばん近い道を選び直す | 1.5 秒で 180° 往復 |
| T6 | 歩行中の頭の揺れ(yaw 振幅 最大 150°) | 窓の中の振幅だけで判定 | 歩いているだけで「首振り」 |

**直し方の型も同じ**で、2 段になる:

- **防波堤**: 出力の側で、短時間の判断の跳びを抑える。T1 は関所(`BearingFlipGate`)を
  入れた。T6 は応答待ちの間だけ受け付ける窓が既にある
- **根治**: 推定に文脈を持たせる。T1 は向き付き線分の map matching(docs/05)、
  T6 は**直前の歩行の振幅を基準線にした増分での判定**(docs/04 の未実装の候補)

**2. T3 は性質が違う。** 推定の誤りではなく、**純音 + 汎用 HRTF では前後の手がかりが
物理的に乗らない**。アルゴリズムをいくら直しても解けない。解ける道は 3 つしかない:

- 前後を使わない(ビーコンは前半球に畳んである・2026-08-31)
- **音源を広帯域にする**(耳介の手がかりが乗る)→ **T5 の判断**
- **首を回して解く**(現実の聴覚と同じ方法)→ **T2 の判断**

つまり **T3 は T2・T5 の下流**にある。単独の作業項目としては、いま入っている補助
(後ろの音を暗くする・メニューで切り替え)の評価だけが残る。

**3. T7 は独立していて安い。** 文書と画面の文言を直すだけ。残すと、公開した配布物と
説明が食い違ったままになる。中身は 2 点:
**接続元の IP が配信先に届くことが書かれていない** / **散歩開始時に自動で取得することが
画面に書かれていない**(説明は「地図を取得」ボタンの節にしか無い)。

### T6 の誤検出率は上がっている(2026-10-26 に測った)

影検出(応答待ち以外で検出器が反応した回数)から、docs/04 と同じ物差しで出した
(`scripts/shadow_rate.awk`)。**「応答までの 3 秒間に誤検出が起きる確率」**:

| 散歩 | うなずき(→ 帰路開始) | 首振り(→ 延長) |
|---|---|---|
| 2026-08-17(閾値を決めた時) | 2% | 9% |
| 2026-09-18 朝 | 5.4% | **20.4%** |
| 2026-09-18 夕方 | 2.7% | **17.8%** |
| 2026-10-25(ポケット・移動) | **8.9%** | 9.4% |

**どちらも 8/17 の値を上回る回がある。** 2026-08-17 の判断は「頻発して困るまで対処しない。
影検出で率は記録され続けるので悪化に気づける」だった。**悪化はこれで見えた。**

ただし条件が揃っていない(装着・歩き方・場所が回ごとに違う)ので、**閾値のせいとは
言い切れない**。うなずきの誤りは帰路が始まってしまう(取り消せない)ので、
首振り(延長・取り返しがつく)より重い。

| 順 | 課題 | 理由 |
|---|---|---|

## 新しい仕組みの課題(T2・T5)— 方向性ごと

### T2: 頭の向き

| 方向性 | 中身 | 状態 | 得るもの | 失うもの |
|---|---|---|---|---|
| A. 使わない | 進行方位だけで定位する | **配布中**(iOS・Android) | 装置が要らない。両 OS で同じ | 立ち止まると方向が消える。首を振っても音が動かない。前後を首で解けない |
| B. イヤホンの姿勢 | AirPods の yaw / 角速度 | **不成立(確定)**。yaw は旋回を追えない(2026-08-19)。角速度も「軸が違う疑い」(2026-10-03 の再生) | — | — |
| C. スマホを頭に固定 | スマホの磁力計で絶対方位(docs/13) | **成立**(学習 194.4° に対し実測 195°)。実験ビルドだけ | 絶対方位。**首で前後が解ける**(T3 が開く) | スマホを頭の後ろに付ける手間。磁気の乱れ(検疫で受ける) |
| D. 外部の 9 軸 | 磁力計入りの頭部ユニット(BNO085 等) | 未着手。実験治具としては有効 | 絶対方位。スマホを自由にできる | 別機器・BLE・自作ファームウェア。**「iPhone + AirPods だけ」から外れる** |
| E. OS の頭部追跡 | Android の `TYPE_HEAD_TRACKER`(API 33) | **未調査** | 標準の仕組み | 対応するイヤホンが限られる見込み(未確認) |

**分かれ目は「装置を足すか」。** 足さない限り A しか残らず(B は確定で不成立)、
足すなら C が唯一の実証済み。C は T3(前後)も同時に開くので、**T2 の判断は T3 の判断を兼ねる**。

### T5: 音源

| 方向性 | 中身 | 状態 | 得るもの | 失うもの |
|---|---|---|---|---|
| a. 利用者が選ぶ | 端末の曲を取り込む | **配布中** | 好きな曲。権利は利用者側 | 選ぶ手間(Android はピッカー)。1 曲だけ。知らない曲との出会いが無い |
| b. 同梱 | 自作 / CC0 をアプリに入れる | 未着手(当初の推奨) | 通信なし。権利が明快 | 曲数が限られて飽きる。容量 |
| c. 配信 | R2 から取る(地図と同じ基盤) | **方針のみ**(2026-08-29 に採用と記録) | 曲数を増やせる | 通信が増える。圏外で鳴らない。権利は自作 / CC0 のみ |
| d. 合成 | 実行時に作る(8bar-digger 型) | **「まず聴く」の提案止まり** | 容量ゼロ。**選ぶ手間ゼロ**。権利問題が無い | 「惹かれる」質が未検証。作曲まで自動化しないと飽きは解けない |
| e. 利用者のライブラリ | MusicKit | 未着手 | 曲数が無限 | DRM・部分再生の制約。空間化できるか未確認 |

**記録と実装が食い違っている。** docs/08 は 2026-08-29 に「配信(c)を採る」と書いたが、
実装されたのは「利用者が選ぶ(a)」(2026-09-08 の最小形から続いている)。
**どちらを本線にするかは整理されていない。**

**比べる軸**: 惹かれる質 / 飽き / 選ぶ手間 / 権利 / 通信と容量 / **定位への向き**
(広帯域なら耳介の手がかりが乗り、T3 に効く。純音に近い音色は T3 を悪化させる)。

### T2・T5 と既存の課題の絡み

```
 T2(頭の向き)──┬──→ T3(前後):C を選べば首で解ける
                 └──→ T6(ジェスチャ):入力源が同じ AirPods の姿勢
 T5(音源)  ──────→ T3(前後):広帯域なら耳介の手がかりが乗る
```

**T3 は T2・T5 のどちらかが決まれば動き出す。** 逆に言うと、T2 と T5 を決めないまま
T3 に手を入れても、いまの補助(後ろを暗くする)以上のことはできない。

## ユーザー体験から見た課題(2026-10-31)

上の T / L / B は作る側の分け方。**使う側から見ると、まとまり方が変わる。**

### 散歩の流れに沿って

| 場面 | 利用者が感じること | 課題 |
|---|---|---|
| 入手・設定 | 何が外へ送られているのか分からない | T7 |
| 出発前 | 曲を自分で用意して選ぶのが面倒。毎回同じ曲になる | T5 |
| 出発前 | 出先から歩き出すと自宅が合わない。その場で直せない | B1 |
| 使い方 | 出先から家へ歩く時に使うと、出た瞬間に「帰りどき」になり散策が無い | B3 |
| 散策中 | 首を振っても音が動かない。立ち止まると方向が消える | T2 |
| 散策中 | 前の音が後ろから聞こえる。スポットを通り過ぎたか分からない | T3 |
| 時間到来 | うなずいていないのに帰路が始まる。首を振っていないのに延長される | T6 |
| 帰路 | 帰る方向の音が左右へ飛ぶ。後ろを指し続ける | T1 |
| 帰路 | 道を無視してまっすぐ指す。**なぜかは分からない** | B2 |
| 帰宅後 | 発見 MAP が空。**なぜかは分からない** | B2 |
| (Android) | そもそも動くか分からない | T4 |

### 体験のテーマ

| | テーマ | 課題 | 要点 |
|---|---|---|---|
| ① | **帰り道を任せられるか** | T1・B1・B2 | 帰路はぶらつくための安全網。作る側の分類では別々だが、**体験としては 1 つの問題** |
| ② | **音の方向を信じられるか** | T2・T3 | 常にある制約で、体験の上限を決めている。P1(方向が信じられる)は 8/19 に達成としたが、**立ち止まった時と前後に限っては崩れたまま** |
| ③ | **自分の意思どおりに動くか** | T6 | うなずきの誤りは帰路が始まり**取り消せない**。直すには画面を見ることになり「画面を見ない」も崩れる |
| ④ | **使い始めやすいか・使える場面** | T5・B1・B3 | 出発前の手間と、使える場面の狭さ。B3 は壊れているのではなく**その使い方がまだ無い** |
| ⑤ | **安心して使えるか** | T7 | 多くの人は気づかないが、気づいた人の信頼を損なう |

**いまの課題は、ほぼ全部が「信じられるか・任せられるか」の側にある。**
「その方向が面白いか(P2)」の側の課題は、この一覧には無い。

### 重さ(頻度 × 起きた時の重さ × 取り返せるか)

| 3 | T6 意図しない帰路開始 | 時間到来 1 回につき数%(影検出からの推定) | 意思に反して帰らされる | **取り消せない** |
| 4 | T2 頭の向き | 常に | 体験の上限を決める | — |
| 5 | T3 前後 | 常に(ビーコンは軽減済み) | 通り過ぎたか分からない | — |
| 6 | B3 家へ向かう移動 | その使い方をした時 | 散策が無い | — |
| 7 | T5 音源 | 出発前に毎回 | 手間と飽き | — |
| 8 | B2 黙る | 劣化した時 | 単独では小さいが、1・2 の劣化を**理由不明**にする | — |

#### T1 の頻度(2026-10-31 に全ログから実測)

`scripts/beacon_flips.sh` を、ビーコンの残っている全ログへ当てた。重複を除いて 11 回:

| | 結果 |
|---|---|
| 90° 超の跳び | **11 回すべてで発生**(1 回の帰路で 1〜16 回) |
| 150° 超(ほぼ反転) | **11 回中 4 回**(8/25・8/31・9/8 名古屋・9/18) |
| 後ろを指した割合 | 0〜29% |

**「帰路で毎回ほぼ反転する」のではない。** 反転は長い帰路に偏って出る(9/8 と 9/18 で計 9 回)。
ビルドが回ごとに違うので、回の間の比較は目安にとどまる。

### 体験から見た順(提案・未決)

技術の整理では T7 → T1 → T6 の順だが、**体験から見ると、帰路の 3 つ(T1・B1・B2)を
先にまとめて出す**のが筋だと考える。T1 の関所は develop に入っているが、まだ配っていない。
