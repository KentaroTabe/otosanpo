# 08. 方針 C: スポットの音楽に惹かれて歩く(2026-08-21 計画)

案内音の代わりに、**離れた場所で音楽が鳴っている**。その音に惹かれて歩く。
近づくほどよく聞こえ、そこまで行けば全曲が聴ける。

docs/06 の方針 A(曲がる所を指す・現行)/ B(道の先から音がする)に対する **3 つ目の方針**。
ブランチを分けて実装し、比べる。

> 「遠くから聞こえる音楽に誘われている」は、2026-08-20 に**ストーリーの候補**として
> 挙がっていたもの(docs/01)。**方針 C はそれを比喩ではなく実体にする。**
> 採用すれば、保留にしていたストーリー付けと音源デザインの両方がここで決まる。

## いまの前提のどこが変わるか

**これは音の調整ではなく、前提の変更である。** 変わるものを先に並べる。

| いまの決定 | 方針 C ではどうなるか |
|---|---|
| 3 原則 1「画面を見ない」 | **緩める。** 近傍に何が流れているかは画面で分かる。試聴もできる |
| 「基本無音・外音取り込み・点の earcon」(docs/01) | **連続音になる。** 採用しなかった「連続 BGM」に正面から抵触する(下記の安全) |
| 散策中の案内 = 分岐提案 + 曲がり角の誘導 | **無くなる。** 曲がる場所は指定せず、音源の方角だけが手がかり |
| 音の語彙 5 種 | 散策中は音楽が担う。earcon は帰路・時間到来・到着に縮む |
| ユーザーの音楽が主役(`duckOthers`) | **アプリが音楽を鳴らす側になる。** 主客が入れ替わる |

変わらないもの:

- **3 原則 2「叱らない」** — むしろ強くなる。音楽は指示ではないので、無視は自然に成立する
- **3 原則 3「約束を守る」** — 帰宅予算はそのまま。スポットは予算の内側からしか選ばない
- **帰路** — 帰路の案内(homeBeacon)は現行のまま。変えるのは散策中だけ
- **送信ゼロ** — 位置は端末内に留める。音源を配信で取る場合だけ例外が要る(判断待ち)

## 2026-08-17 の「音楽で案内する」考察との関係

docs/03 に、**利用者の音楽の定位を動かして方向を伝える**案を検討して**却下**した記録がある。
方針 C は却下した案とは別物だが、**5 つの反論のうち 3 つはそのまま残る。**

| 当時の反論 | 方針 C ではどうか |
|---|---|
| 実装できない(他アプリの音は加工できない) | **消える。** 当時「唯一の道」とした *アプリ自身が音楽を鳴らす* を採る |
| 1. 音楽そのものを壊す | **消える。** 音楽は目的ではなく道標。空間に置かれるのが前提の音 |
| 2. 基準が無い(連続音には「いま鳴った」が無い) | **残る。** ただし音源が世界の 1 点に居る限り「あちらから聞こえる」は成立しうる |
| 3. 慣れて気づかなくなる | **残る。** 曲が変わる・近づくと変化する、で持たせられるかは未知 |
| 4. 頭の向きへの依存が強くなる | **残る。しかも悪化する**(下記) |
| 5. 安全性(環境音のマスク) | **残る。最大の懸念**(下記) |

## 危ないところ(実装より先に潰す)

### 1. 頭の向きが取れないことの影響が、点の音より大きい

AirPods の yaw は**旋回を追えていない**(2026-08-19 実測・`use_head_orientation` は false)。
定位の基準は進行方位しかない。

- 点の earcon なら、首を振っている最中に鳴らなければ破綻は見えない
- **鳴り続ける音源は、首を振るたびに一緒に回る。** 「世界の 1 点で鳴っている」感じが壊れる
- 立ち止まると course が失われる(15 秒のホールドの後は方向なし)。
  **交差点で立ち止まって「どっちから聞こえる?」と考える瞬間**が、いちばん方向を失いやすい

先に決めること: 方向を失った時にどう振る舞うか(中央に寄せる / 直前の向きを保つ / 音量だけ残す)。

#### ハードウェアで解決できるか(2026-08-21 の問い)

**ジャイロは既に載っている。読んでいないだけ。** `CMHeadphoneMotionManager` が返す
`CMDeviceMotion` には `attitude` のほかに `rotationRate`(角速度 = ジャイロ)があるが、
`HeadphoneMotionService` は `attitude.pitch` と `attitude.yaw` しか取り出していない。

**同じジャイロを足しても直らない。** ヨーは原理的にジャイロだけでは絶対化できない。

| 軸 | 絶対の基準になるもの | 結果 |
|---|---|---|
| ピッチ・ロール | 重力(加速度計) | 補正できる。ドリフトしない |
| **ヨー** | **磁気か外部参照しかない** | ジャイロだけでは積分ドリフトが溜まり続ける |

AirPods は加速度計とジャイロを持つが、`CMHeadphoneMotionManager` は参照枠を選べず、
磁北基準の絶対方位は取れない(`CMDeviceMotion.heading` が有効値を返すかは**未確認**。
1 行のログで確かめられるので、次に触るとき見る価値はある)。
iPhone 側の磁力計はポケットの中で脚と一緒に振れるので、頭の基準には使えない。

**解決するハードウェアは「9 軸(磁力計入り)の頭部ユニット」。** BNO085 のような
フュージョン IMU は絶対方位まで出すので、**立ち止まって首を回す場合まで解ける**。

- 代償: 別のものを被って充電して繋ぐ / BLE の自作ファームウェア /
  **鉄骨・車の近くで磁気が乱れる**(端末コンパスが左右を反転させた前例あり・docs/04)
- そして **「iPhone + AirPods だけ」というゴール(docs/01)から外れる。** App Store で
  配れる形ではなくなる
- ただし**実験治具としては有効**。「頭の向きが正しく取れたら体験はどう変わるか」を
  一度だけ確かめる装置と割り切るなら、方針 C の是非を判断する材料になる

**その前に、ハード無しで試せることが 2 つある。**

1. **`rotationRate.z` を短い窓で積分し、時間で 0 へ戻す**(docs/06 柱 2 に案として記載済み)。
   数秒ならドリフトは無視できる。**必要なのは「音楽の方を見た数秒」だけ**で、
   頭は平均すれば正面を向くという前提を使う。絶対基準を持たないので飛びの影響も受けない
2. **yaw を否定した測り方を検算する。** 判定は GPS の course を正解として使っているが、
   実測の `courseAccuracy` は 40〜70° で、2 秒間隔の `|Δcourse| ≥ 30°` には
   曲がっていない雑音が混ざる。さらに判定は `|Δyaw| ≥ 10°` の対だけを見ており、
   「頭が動いた時に course と合ったか」を問うている。**course を数秒ならしてから
   測り直すと結論が変わる可能性がある。** ログは手元にあるので歩かずに試せる

**方針 C にとってどちらが要るかは、場面で分かれる。**

| 場面 | 何が要るか | ハードは要るか |
|---|---|---|
| 歩いている間 | course(絶対)は取れている。**頭と進行方向のずれ**だけ分かればよい | **要らない**(上記 1 で足りる見込み) |
| 立ち止まっている間 | course が無い。**頭の絶対方位**が要る | 要る — **または方向を出さない設計にする** |

後者には方針 C 固有の逃げ道がある。**方針 C は画面を許すので、立ち止まった時の
方向探しは画面が担える。** 止まったら音量だけ残して方向は出さず、知りたければ画面を見る。
ハードを足さずに最悪の場面を回避できる。

**順番の提案: 無料(2)→ 小さい実装(1)→ それでも足りなければ治具としての 9 軸。**

### 2. 連続音は環境音を覆う

「基本無音・外音取り込み」は**安全のための判断**だった(docs/01)。連続再生はこれを覆す。
覆すなら、覆すと明示したうえで代わりの担保を置く。

- 音量の上限を設ける(現地でも「会話が聞こえる」程度)
- 外音取り込み前提の案内をオンボーディングに置く(アプリからは制御できない)
- 交差点・幹線道路の近くでは下げる案(`WalkMap` の `cross` と `WayClass` を使えば判定できる)

### 3. 音源へまっすぐ引かれると、また街区を突っ切る

2026-08-20 に直したばかりの問題と同じ形になりうる。ただし**今回は直線で正しい**と考える。

> 現実の音は直線で聞こえる。**どう近づくかは本人が選ぶ** — それは「叱らない」に合う。

代わりに**選定側で担保する**。`RouteField` で自宅からの経路コストが引ける以上、
**歩いて到達できない場所(川の対岸・立入禁止)にスポットを置かない**ことは判定できる。

## 体験の骨格

```
出発前  近傍に何が流れているかを画面で見る(任意)。数秒の試聴ができる
  ↓
散策中  最も近いスポットの音楽が、距離に応じた聞こえ方で鳴り続ける
  ↓     近づくほど大きく・明瞭になる(遠いうちは高域が落ち、残響が乗る)
到達    全曲が鳴る。ここでしか全部は聴けない
  ↓
次へ    次のスポットが聞こえ始める
  ↓
時間到来 → うなずき → 帰路(ここから先は現行のまま。音楽は止める)
```

## 設計の柱

### 柱 1: 音 — 距離を「音量 + 音色 + 残響」で表す

誘導とビーコンで**距離は音量**と決めた(docs/03)。音楽は帯域が広いので、
音量だけでなく**現実の距離減衰**を模せる。

| 手がかり | 遠い | 近い |
|---|---|---|
| 音量 | 小 | 大 |
| 高域 | 落ちる(ローパス) | 開く |
| 残響 | 多い(遠くの音は反射が主) | 少ない |
| 内容 | 一部だけ(ループ) | 全曲 |

- 写像は **Core に置く**(`SpotAudio`)。数値は `config/parameters.json`
- **広帯域なので HRTF の前後判別が効く可能性がある。** 純音のビーコンで前後が
  判別できなかったのは 4〜10 kHz の成分が無かったためと分析済み(docs/03)。
  音楽なら耳介のスペクトル手がかりを運べる。**効くなら「振り返る」が体験に入る**
- 実機に出る前に机上で聴ける(下記 段 0)

### 柱 2: スポット — どこに置くか

置き場の候補を出す材料は**すでに全部ある**。

| 使うもの | 何に効くか |
|---|---|
| `ZoneMap`(300 m 角・道の総延長で重み付け) | 未踏で道のある地帯を選ぶ |
| `VisitGrid`(歩いた距離で減衰する馴染み度) | 通い慣れた場所には置かない |
| `RouteField`(自宅からの経路コスト) | 到達できること・帰宅予算の内側であること |
| `WalkGraph`(道の上の点) | **道の上に置く**(私有地・水面に置かない) |

- 1 回の散歩で会えるのは 2〜4 個を目安にする(多いと巡回作業になる)
- 同じ場所には同じ曲を置くか、毎回変えるか → 判断待ち(場所の記憶になるか、飽きるか)

### 柱 3: 音源 — 何を鳴らすか(**最大の判断待ち**)

| 案 | 良い点 | 悪い点 |
|---|---|---|
| a. 同梱(自作 or CC0) | オフライン・権利が明快・送信ゼロを守れる | 曲数が限られ、飽きる。容量 |
| b. 利用者のライブラリ(MusicKit) | 曲数が無限・好きな曲に呼ばれる | DRM と部分再生の制約・**知らない曲との出会いが無い** |
| c. その場で合成 | 無限・容量ゼロ | 「惹かれる」質に届くかは疑わしい |

**まず a で作るのを勧める。** 距離の写像とスポットの置き方は音源の出どころに依存しないので、
a で体験を確かめてから b/c を検討できる。CC BY はクレジット運用が煩雑なので避ける(docs/03)。

### 柱 4: 画面 — 近傍に何が流れているか

**今日作った経路図の道具がそのまま使える**(`MapFrame` / `WalkGraph.roadSegments` / Canvas)。

- 近傍のスポット一覧: 方角・距離・曲(名前 or 雰囲気)・**数秒の試聴**
- 地図は端末内の経路データで描く(送信なし)
- 見るのは出発前と立ち止まった時、という運用を推奨(歩きながらは見ない)

### 柱 5: 裁定 — 既存の音との関係

現行の優先順位は **プロンプト > 誘導 > 提案 > ビーコン**(docs/03)。音楽はこの列に入らない。

> **音楽は「地」、earcon は「図」。** earcon が鳴る瞬間だけ音楽を下げる
> (いま他アプリに対してしている `duckOthers` を、自前の再生に対して行う)。

- 時間到来・確認音・到着音は今までどおり
- **帰路に入ったら音楽は止める。** 「帰る」が伝わらなくなるため(判断待ち)

## 実装の切れ目と実験

**散歩でしか分からないのは「音楽に惹かれて歩けるか」だけ。** それ以外は机上で潰す。

| 段 | やること | 机上での確かめ方 | 散歩で見るもの |
|---|---|---|---|
| 0 | 距離の写像 | **`Sources/Demo` を拡張し、200/100/50/20/0 m の聞こえ方を書き出して聴き比べる。** 前後(HRTF)も同様 | — |
| 1 | スポットの選定 | 過去のログの経路に対して、どこに立ちどう聞こえたはずかを再生で出す | — |
| 2 | 再生の配線(音楽 + earcon の裁定) | 実機で立ったまま確認(歩かない) | — |
| 3 | 画面(近傍・試聴) | シミュレータ | — |
| 4 | 通し | — | **散歩 1 回。意図的に試すのは「音のする方へ歩く」と「立ち止まって方向が分かるか」の 2 つ** |

**段 0 で止まる可能性がある。** 距離が聞き分けられない音になったら、その先を作っても意味がない。
段 0 は歩かずに終わるので、そこで方針 C の是非まで判断できる。

- 段 0 は macOS の `AVAudioEngine` を手動レンダリングで回し、**実機と同じ音響グラフ**で
  書き出すのが理想(HRTF と残響まで机上で聴ける)。macOS で HRTF が同じに掛かるかは
  **未確認**。掛からなければ、Core 側の写像(音量・ローパス)だけを軟件で当てて聴く
- 段 1 の再生ツールは既存の `scripts/replay_log.sh` の枠組みに載る

## 改訂(2026-08-29)— 頭部固定を前提にし、音楽は配信で取る

利用者判断で 2 つが決まり、計画の前提が変わった。

### 1. 頭部固定(docs/13)を前提に格上げ

判断待ち 8 の決着。**危険 1(頭の向き)は装置で解く。**

- 歩行中の首振りも、**立ち止まって「どっちから聞こえる?」と探す場面**も、
  絶対方位で成立する。「停止中は画面に逃がす」という代替案は不要になった
- **前後の判別も開く**: 音楽は広帯域なので HRTF の手がかりが乗り、
  首を振れば現実の聴覚と同じ方法で前後が解ける(柱 1 の期待が装置で補強される)
- 代わりに**柱 4(画面)と装着が衝突する**: 画面は額にあり、歩行中は見えない。
  柱 4 は「**出発前(装着前)**に近傍と試聴を見る」に限定する。
  到達時に外して見るのは任意(装置の付け外しは自由)
- **磁気の乱れ**という新しい障壁を docs/13 の検疫で受ける。連続音は点の音より
  乱れの影響が長く続くので、乱れ判定中は**方位を出さず音量だけ残す**

柱 1 に 1 つ追加: **近距離の方位ふらつき**。音源の方位は自分の位置から計算するので
GPS 誤差(実測 3〜6 m)がそのまま角度誤差になる(20 m 先で 14°・10 m 先で 27°)。
`spot_direction_min_distance_m`(仮 20 m)以内は方位を出さず、音量と「全曲」で表す。

### 2. 音源は配信で取る(柱 3 の改訂)

同梱(案 a)ではなく **d. 配信(R2)** を採る。地図のタイル配信(docs/12)と
同じ基盤・同じ約束の枠内で音楽を取れるようになったため。

```
<公開 URL>/music/index.json   曲の一覧(id・ファイル名・バイト数・長さ・雰囲気タグ)
<公開 URL>/music/<id>.m4a     曲本体(AAC 128 kbps ≈ 1 MB/分)
```

- **権利は自作か CC0 のみ**(CC BY はクレジット運用が煩雑・docs/03 の判断を踏襲)
- 取得の時機: **散歩開始時にスポットを選定し、割り当てた曲を先読み**
  (タイルの自動取得と同じ「足りない分だけ・裏で」)。
  2〜4 スポット × 2〜3 MB ≈ **5〜10 MB / 散歩**。キャッシュして再利用
- **プライバシー**: 曲 ID は場所に紐づかない(スポットへの割り当ては端末内)。
  送る情報はタイル取得を超えない。**通信量は増える**(docs/12 の記述を更新すること)
- 圏外・失敗時: 曲が無いスポットは**鳴らさない**(方針 C 自体が成立しないので、
  その散歩は方針 A / B の動きに退避する)

### 方針 B との関係

B(docs/14)は「音に向かって歩く」の骨格を earcon だけで検証できる。
**B が成立するなら、C はその lure を「実在のスポット + 音楽」に置き換えた形**になる。
逆に B で「音に向かって歩くのがそもそも快くない」と分かれば、C の作り込みを省ける。
順序は判断待ち(docs/14 判断待ち 3)。
