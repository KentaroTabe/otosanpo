# 08. 方針 C: スポットの音楽に惹かれて歩く(2026-08-21 計画)

案内音の代わりに、**離れた場所で音楽が鳴っている**。その音に惹かれて歩く。
近づくほどよく聞こえ、そこまで行けば全曲が聴ける。

docs/06 の方針 A(曲がる所を指す・現行)/ B(道の先から音がする)に対する **3 つ目の方針**。
ブランチを分けて実装し、比べる。

> 「遠くから聞こえる音楽に誘われている」は、2026-08-20 に**ストーリーの候補**として
> 挙がっていたもの(docs/01)。**方針 C はそれを比喩ではなく実体にする。**
> 採用すれば、保留にしていたストーリー付けと音源デザインの両方がここで決まる。

## いまの前提のどこが変わるか

**これは音の調整ではなく、前提の変更である。** 変わるものを先に並べる。

| いまの決定 | 方針 C ではどうなるか |
|---|---|
| 3 原則 1「画面を見ない」 | **緩める。** 近傍に何が流れているかは画面で分かる。試聴もできる |
| 「基本無音・外音取り込み・点の earcon」(docs/01) | **連続音になる。** 採用しなかった「連続 BGM」に正面から抵触する(下記の安全) |
| 散策中の案内 = 分岐提案 + 曲がり角の誘導 | **無くなる。** 曲がる場所は指定せず、音源の方角だけが手がかり |
| 音の語彙 5 種 | 散策中は音楽が担う。earcon は帰路・時間到来・到着に縮む |
| ユーザーの音楽が主役(`duckOthers`) | **アプリが音楽を鳴らす側になる。** 主客が入れ替わる |

変わらないもの:

- **3 原則 2「叱らない」** — むしろ強くなる。音楽は指示ではないので、無視は自然に成立する
- **3 原則 3「約束を守る」** — 帰宅予算はそのまま。スポットは予算の内側からしか選ばない
- **帰路** — 帰路の案内(homeBeacon)は現行のまま。変えるのは散策中だけ
- **散歩履歴は端末内保存** — この方針 C の検討時点では位置送信ゼロを前提にしていたが、
  Hot Pepper 連携後は周辺店舗候補の取得時だけ現在地を外部 API へ送る。
  音源を配信で取る場合はさらに別の説明が要る(判断待ち)

## 2026-08-17 の「音楽で案内する」考察との関係

docs/03 に、**利用者の音楽の定位を動かして方向を伝える**案を検討して**却下**した記録がある。
方針 C は却下した案とは別物だが、**5 つの反論のうち 3 つはそのまま残る。**

| 当時の反論 | 方針 C ではどうか |
|---|---|
| 実装できない(他アプリの音は加工できない) | **消える。** 当時「唯一の道」とした *アプリ自身が音楽を鳴らす* を採る |
| 1. 音楽そのものを壊す | **消える。** 音楽は目的ではなく道標。空間に置かれるのが前提の音 |
| 2. 基準が無い(連続音には「いま鳴った」が無い) | **残る。** ただし音源が世界の 1 点に居る限り「あちらから聞こえる」は成立しうる |
| 3. 慣れて気づかなくなる | **残る。** 曲が変わる・近づくと変化する、で持たせられるかは未知 |
| 4. 頭の向きへの依存が強くなる | **残る。しかも悪化する**(下記) |
| 5. 安全性(環境音のマスク) | **残る。最大の懸念**(下記) |

## 危ないところ(実装より先に潰す)

### 1. 頭の向きが取れないことの影響が、点の音より大きい

AirPods の yaw は**旋回を追えていない**(2026-08-19 実測・`use_head_orientation` は false)。
定位の基準は進行方位しかない。

- 点の earcon なら、首を振っている最中に鳴らなければ破綻は見えない
- **鳴り続ける音源は、首を振るたびに一緒に回る。** 「世界の 1 点で鳴っている」感じが壊れる
- 立ち止まると course が失われる(15 秒のホールドの後は方向なし)。
  **交差点で立ち止まって「どっちから聞こえる?」と考える瞬間**が、いちばん方向を失いやすい

先に決めること: 方向を失った時にどう振る舞うか(中央に寄せる / 直前の向きを保つ / 音量だけ残す)。

#### ハードウェアで解決できるか(2026-08-21 の問い)

**ジャイロは既に載っている。読んでいないだけ。** `CMHeadphoneMotionManager` が返す
`CMDeviceMotion` には `attitude` のほかに `rotationRate`(角速度 = ジャイロ)があるが、
`HeadphoneMotionService` は `attitude.pitch` と `attitude.yaw` しか取り出していない。

**同じジャイロを足しても直らない。** ヨーは原理的にジャイロだけでは絶対化できない。

| 軸 | 絶対の基準になるもの | 結果 |
|---|---|---|
| ピッチ・ロール | 重力(加速度計) | 補正できる。ドリフトしない |
| **ヨー** | **磁気か外部参照しかない** | ジャイロだけでは積分ドリフトが溜まり続ける |

AirPods は加速度計とジャイロを持つが、`CMHeadphoneMotionManager` は参照枠を選べず、
磁北基準の絶対方位は取れない(`CMDeviceMotion.heading` が有効値を返すかは**未確認**。
1 行のログで確かめられるので、次に触るとき見る価値はある)。
iPhone 側の磁力計はポケットの中で脚と一緒に振れるので、頭の基準には使えない。

**解決するハードウェアは「9 軸(磁力計入り)の頭部ユニット」。** BNO085 のような
フュージョン IMU は絶対方位まで出すので、**立ち止まって首を回す場合まで解ける**。

- 代償: 別のものを被って充電して繋ぐ / BLE の自作ファームウェア /
  **鉄骨・車の近くで磁気が乱れる**(端末コンパスが左右を反転させた前例あり・docs/04)
- そして **「iPhone + AirPods だけ」というゴール(docs/01)から外れる。** App Store で
  配れる形ではなくなる
- ただし**実験治具としては有効**。「頭の向きが正しく取れたら体験はどう変わるか」を
  一度だけ確かめる装置と割り切るなら、方針 C の是非を判断する材料になる

**その前に、ハード無しで試せることが 2 つある。**

1. **`rotationRate.z` を短い窓で積分し、時間で 0 へ戻す**(docs/06 柱 2 に案として記載済み)。
   数秒ならドリフトは無視できる。**必要なのは「音楽の方を見た数秒」だけ**で、
   頭は平均すれば正面を向くという前提を使う。絶対基準を持たないので飛びの影響も受けない
2. **yaw を否定した測り方を検算する。** 判定は GPS の course を正解として使っているが、
   実測の `courseAccuracy` は 40〜70° で、2 秒間隔の `|Δcourse| ≥ 30°` には
   曲がっていない雑音が混ざる。さらに判定は `|Δyaw| ≥ 10°` の対だけを見ており、
   「頭が動いた時に course と合ったか」を問うている。**course を数秒ならしてから
   測り直すと結論が変わる可能性がある。** ログは手元にあるので歩かずに試せる

**方針 C にとってどちらが要るかは、場面で分かれる。**

| 場面 | 何が要るか | ハードは要るか |
|---|---|---|
| 歩いている間 | course(絶対)は取れている。**頭と進行方向のずれ**だけ分かればよい | **要らない**(上記 1 で足りる見込み) |
| 立ち止まっている間 | course が無い。**頭の絶対方位**が要る | 要る — **または方向を出さない設計にする** |

後者には方針 C 固有の逃げ道がある。**方針 C は画面を許すので、立ち止まった時の
方向探しは画面が担える。** 止まったら音量だけ残して方向は出さず、知りたければ画面を見る。
ハードを足さずに最悪の場面を回避できる。

**順番の提案: 無料(2)→ 小さい実装(1)→ それでも足りなければ治具としての 9 軸。**

### 2. 連続音は環境音を覆う

「基本無音・外音取り込み」は**安全のための判断**だった(docs/01)。連続再生はこれを覆す。
覆すなら、覆すと明示したうえで代わりの担保を置く。

- 音量の上限を設ける(現地でも「会話が聞こえる」程度)
- 外音取り込み前提の案内をオンボーディングに置く(アプリからは制御できない)
- 交差点・幹線道路の近くでは下げる案(`WalkMap` の `cross` と `WayClass` を使えば判定できる)

### 3. 音源へまっすぐ引かれると、また街区を突っ切る

2026-08-20 に直したばかりの問題と同じ形になりうる。ただし**今回は直線で正しい**と考える。

> 現実の音は直線で聞こえる。**どう近づくかは本人が選ぶ** — それは「叱らない」に合う。

代わりに**選定側で担保する**。`RouteField` で自宅からの経路コストが引ける以上、
**歩いて到達できない場所(川の対岸・立入禁止)にスポットを置かない**ことは判定できる。

## 体験の骨格

```
出発前  近傍に何が流れているかを画面で見る(任意)。数秒の試聴ができる
  ↓
散策中  最も近いスポットの音楽が、距離に応じた聞こえ方で鳴り続ける
  ↓     近づくほど大きく・明瞭になる(遠いうちは高域が落ち、残響が乗る)
到達    全曲が鳴る。ここでしか全部は聴けない
  ↓
次へ    次のスポットが聞こえ始める
  ↓
時間到来 → うなずき → 帰路(ここから先は現行のまま。音楽は止める)
```

## 設計の柱

### 柱 1: 音 — 距離を「音量 + 音色 + 残響」で表す

誘導とビーコンで**距離は音量**と決めた(docs/03)。音楽は帯域が広いので、
音量だけでなく**現実の距離減衰**を模せる。

| 手がかり | 遠い | 近い |
|---|---|---|
| 音量 | 小 | 大 |
| 高域 | 落ちる(ローパス) | 開く |
| 残響 | 多い(遠くの音は反射が主) | 少ない |
| 内容 | 一部だけ(ループ) | 全曲 |

- 写像は **Core に置く**(`SpotAudio`)。数値は `config/parameters.json`
- **広帯域なので HRTF の前後判別が効く可能性がある。** 純音のビーコンで前後が
  判別できなかったのは 4〜10 kHz の成分が無かったためと分析済み(docs/03)。
  音楽なら耳介のスペクトル手がかりを運べる。**効くなら「振り返る」が体験に入る**
- 実機に出る前に机上で聴ける(下記 段 0)

### 柱 2: スポット — どこに置くか

置き場の候補を出す材料は**すでに全部ある**。

| 使うもの | 何に効くか |
|---|---|
| `ZoneMap`(300 m 角・道の総延長で重み付け) | 未踏で道のある地帯を選ぶ |
| `VisitGrid`(歩いた距離で減衰する馴染み度) | 通い慣れた場所には置かない |
| `RouteField`(自宅からの経路コスト) | 到達できること・帰宅予算の内側であること |
| `WalkGraph`(道の上の点) | **道の上に置く**(私有地・水面に置かない) |

- 1 回の散歩で会えるのは 2〜4 個を目安にする(多いと巡回作業になる)
- 同じ場所には同じ曲を置くか、毎回変えるか → 判断待ち(場所の記憶になるか、飽きるか)

### 柱 3: 音源 — 何を鳴らすか(**最大の判断待ち**)

| 案 | 良い点 | 悪い点 |
|---|---|---|
| a. 同梱(自作 or CC0) | オフライン・権利が明快・送信ゼロを守れる | 曲数が限られ、飽きる。容量 |
| b. 利用者のライブラリ(MusicKit) | 曲数が無限・好きな曲に呼ばれる | DRM と部分再生の制約・**知らない曲との出会いが無い** |
| c. その場で合成 | 無限・容量ゼロ | 「惹かれる」質に届くかは疑わしい |

**まず a で作るのを勧める。** 距離の写像とスポットの置き方は音源の出どころに依存しないので、
a で体験を確かめてから b/c を検討できる。CC BY はクレジット運用が煩雑なので避ける(docs/03)。

### 柱 4: 画面 — 近傍に何が流れているか

**今日作った経路図の道具がそのまま使える**(`MapFrame` / `WalkGraph.roadSegments` / Canvas)。

- 近傍のスポット一覧: 方角・距離・曲(名前 or 雰囲気)・**数秒の試聴**
- 地図は端末内の経路データで描く(送信なし)
- 見るのは出発前と立ち止まった時、という運用を推奨(歩きながらは見ない)

### 柱 5: 裁定 — 既存の音との関係

現行の優先順位は **プロンプト > 誘導 > 提案 > ビーコン**(docs/03)。音楽はこの列に入らない。

> **音楽は「地」、earcon は「図」。** earcon が鳴る瞬間だけ音楽を下げる
> (いま他アプリに対してしている `duckOthers` を、自前の再生に対して行う)。

- 時間到来・確認音・到着音は今までどおり
- **帰路に入ったら音楽は止める。** 「帰る」が伝わらなくなるため(判断待ち)

## 実装の切れ目と実験

**散歩でしか分からないのは「音楽に惹かれて歩けるか」だけ。** それ以外は机上で潰す。

| 段 | やること | 机上での確かめ方 | 散歩で見るもの |
|---|---|---|---|
| 0 | 距離の写像 | **`Sources/Demo` を拡張し、200/100/50/20/0 m の聞こえ方を書き出して聴き比べる。** 前後(HRTF)も同様 | — |
| 1 | スポットの選定 | 過去のログの経路に対して、どこに立ちどう聞こえたはずかを再生で出す | — |
| 2 | 再生の配線(音楽 + earcon の裁定) | 実機で立ったまま確認(歩かない) | — |
| 3 | 画面(近傍・試聴) | シミュレータ | — |
| 4 | 通し | — | **散歩 1 回。意図的に試すのは「音のする方へ歩く」と「立ち止まって方向が分かるか」の 2 つ** |

**段 0 で止まる可能性がある。** 距離が聞き分けられない音になったら、その先を作っても意味がない。
段 0 は歩かずに終わるので、そこで方針 C の是非まで判断できる。

- 段 0 は macOS の `AVAudioEngine` を手動レンダリングで回し、**実機と同じ音響グラフ**で
  書き出すのが理想(HRTF と残響まで机上で聴ける)。macOS で HRTF が同じに掛かるかは
  **未確認**。掛からなければ、Core 側の写像(音量・ローパス)だけを軟件で当てて聴く
- 段 1 の再生ツールは既存の `scripts/replay_log.sh` の枠組みに載る

## 改訂(2026-08-29)— 頭部固定を前提にし、音楽は配信で取る

利用者判断で 2 つが決まり、計画の前提が変わった。

### 1. 頭部固定(docs/13)を前提に格上げ

判断待ち 8 の決着。**危険 1(頭の向き)は装置で解く。**

- 歩行中の首振りも、**立ち止まって「どっちから聞こえる?」と探す場面**も、
  絶対方位で成立する。「停止中は画面に逃がす」という代替案は不要になった
- **前後の判別も開く**: 音楽は広帯域なので HRTF の手がかりが乗り、
  首を振れば現実の聴覚と同じ方法で前後が解ける(柱 1 の期待が装置で補強される)
- 代わりに**柱 4(画面)と装着が衝突する**: 画面は額にあり、歩行中は見えない。
  柱 4 は「**出発前(装着前)**に近傍と試聴を見る」に限定する。
  到達時に外して見るのは任意(装置の付け外しは自由)
- **磁気の乱れ**という新しい障壁を docs/13 の検疫で受ける。連続音は点の音より
  乱れの影響が長く続くので、乱れ判定中は**方位を出さず音量だけ残す**

柱 1 に 1 つ追加: **近距離の方位ふらつき**。音源の方位は自分の位置から計算するので
GPS 誤差(実測 3〜6 m)がそのまま角度誤差になる(20 m 先で 14°・10 m 先で 27°)。
`spot_direction_min_distance_m`(仮 20 m)以内は方位を出さず、音量と「全曲」で表す。

### 2. 音源は配信で取る(柱 3 の改訂)

同梱(案 a)ではなく **d. 配信(R2)** を採る。地図のタイル配信(docs/12)と
同じ基盤・同じ約束の枠内で音楽を取れるようになったため。

```
<公開 URL>/music/index.json   曲の一覧(id・ファイル名・バイト数・長さ・雰囲気タグ)
<公開 URL>/music/<id>.m4a     曲本体(AAC 128 kbps ≈ 1 MB/分)
```

- **権利は自作か CC0 のみ**(CC BY はクレジット運用が煩雑・docs/03 の判断を踏襲)
- 取得の時機: **散歩開始時にスポットを選定し、割り当てた曲を先読み**

### 方針 B との関係

## 最小形を 1 つだけ実装した(2026-09-08・利用者判断)

計画のままだった方針 C から、**連続音が方向を伝えるか**という一点だけを取り出して
実装した。次の散歩(画面を見ないテスト・docs/05)に相乗りさせる。

| | |
|---|---|
| 個数 | **1 つだけ**。出発地点から **100 m 以内** |
| いつ決める | **出発前に画面で選んだ時だけ**。歩き出したら画面は見えない |
| 鳴り方 | **一度だけ**。着いたら止まる。最後まで鳴り終わっても止まる |
| 定位 | **前半球へ畳まない**(利用者判断)。通り過ぎれば後ろから聞こえる |
| 距離 | 音量で伝える(ビーコンと同じ形の写像を再利用) |
| 基準 | ビーコン・誘導と同じ resolver。**頭部固定が効けば首に追従する** |
| 音源 | **リポジトリにもアプリにも同梱しない。** Documents に置いたものを名前順で 1 つ |

置き場所は 30° 刻みの候補を作り、地図があれば**道へスナップ**して、狙う距離
(既定 80 m)にいちばん近いものを選ぶ。同点は方位の小さい方 — **再現できるように**。

含まないもの: 複数スポット・再訪・音楽の配信・スポットの編集画面・
「音楽が主役」の音量設計。これらは計画のまま(上記)。

パラメータは `config/parameters.json` の `experiment` にある
(`music_spot_*` の 9 項目。一覧は [docs/13](13_head_mount.md) の設定表)。
**すべて仮置き**で、連続音の音量と距離の対応は歩かないと決まらない。

### 1 回歩いた結果(2026-09-08)— 本実装へ進む判断

> 連続音についてはかなり散歩に対して価値を上げる効果があると思われるので
> 本実装に進めたい(利用者)

**方針 C の賭け(連続音なら聴きながら向きを直せる)は、体感として当たった。**
実装は最小形のままだが、方向を上げる価値があると判断された。

直した 3 点(→ [docs/05](05_field_test.md) の 2026-09-08 の節に実測):

- 定位を**位置更新(1 Hz)にだけ**乗せていたので、首を回してから音が動くまで
  最大 1 秒かかっていた。**頭方位の受信(10 Hz)からも付け直す**
- 素の `.HRTF` は角度の分解能が粗く「向きが 8 段階ほどしかない」と感じられた。
  連続音は **`.HRTFHQ`**。点の earcon は一瞬なので粗さが出にくいが、鳴り続ける音では効く
- **「着いたら止める」は構造的に毎回失敗する。** スポットは出発点の 100 m 以内に置き、
  出発点は自宅なので、**帰り着く手前で必ず「着いた」が起きる**。実測で 80 秒の無音。
  **着いても止めない**ようにした。通り過ぎれば背後に回って自然に遠ざかる

残っている論点(判断待ち): 音楽 977 行のうち **27% が背後**で、
そのとき音量は下限の 0.25 だった。「背後 + 下限」は聞こえていても気づきにくい。
遠距離の音量を上げるか、スポットを経路上に複数置くか(= 本体の設計)。

### 前後を音量で伝える(2026-09-10 利用者依頼)

> スポットが左右にあることは分かるが**前後が分からない**

**前後は HRTF では伝わらない**と 2026-08-18 に確定している(docs/03)。
残る手は「**近づけば大きく・遠ざかれば小さく**」しかない。

線形の写像をやめ、**逆二乗則**(現実の音の減り方)にした。
線形では遠い側で 10 m 動いてもほとんど変わらなかった —
15〜240 m を 0.9〜0.25 に張ると 10 m で 0.027 = **0.3 dB 弱**。
人が気づくのは **1 dB 前後**、3 dB ではっきり分かる。

いまの設定(基準 15 m・減り方 1.0・上限 0.9・下限 0.08)での 10 m あたりの差:

| そこから 10 m 近づくと | |
|---|---|
| 30 m → 20 m | **3.5 dB**(はっきり分かる) |
| 50 m → 40 m | **1.9 dB** |
| 80 m → 70 m | **1.2 dB** |
| 100 m → 90 m | **0.9 dB**(気づける下限あたり) |

スポットは散歩時間に比例した帯(30 分なら 75〜105 m)に置くので、
**その帯の全域で「10 m 近づけば気づける」**。単体テストで固定した。

**この考え方は 2026-09-11 に置き換えた(下記)。** 帯の中なら気づけても、音楽は
帯の外(頭の向きを待つ間に遠ざかった先)で鳴り始めることがあった。

### 音量は鳴り始めた地点から割り振る(2026-09-11 利用者依頼)

3 人の散歩(2026-09-10・docs/05)で、音楽はスポットから **135 m / 95 m / 43 m** の所で
鳴り始めた(頭の向きを待つ上限 120 秒の間に遠ざかっていた)。逆二乗則は遠い側で平らなので、
開発者の散歩では 95 m から 39 m まで近づいても音量の幅は 7.7 dB(10 m あたり約 1.4 dB)で、
感想は「音量の変化も見られない」だった。

利用者の依頼:

> 音楽が流れ始めた地点(またはスタート地点)とスポットの距離に応じて、10m あたりの音量差を変更する

**鳴り始めた地点で下限、スポットの手前(`music_spot_reference_distance_m` = 15 m)で上限とし、
その間を dB で均等につなぐ。** 10 m あたりの差は

    幅 [dB] × 10 ÷ (鳴り始めた距離 − 15 m)     幅 = 20·log10(上限 0.9 ÷ 下限 0.08) ≈ 21 dB

なので、遠くで鳴り始めた散歩ほど小さく、近くで鳴り始めた散歩ほど大きい。
dB で均等にするのは、人の音量の感じ方が対数に近いため(どこでも同じ手応え)。

| 鳴り始めた距離 | 10 m あたり | 旧・逆二乗則でその距離から 10 m |
|---|---|---|
| 135 m(散歩 1) | **1.8 dB** | 約 0.7 dB |
| 95 m(散歩 2) | **2.6 dB** | 約 1.0 dB |
| 43 m(散歩 3) | **7.0 dB**(最小の長さ 30 m に広げる) | 約 2.3 dB |

- **スポットそのものを、鳴り始める地点から置く**ようにした(下記)。起点は置いた距離
  そのもので、帯の中(30 分なら 75〜105 m)に収まる。10 m あたりはおおむね 2.3〜3.5 dB
- 鳴り始めた地点より遠ざかったら下限のまま、15 m より近づいたら上限のまま
- 鳴り始めた地点がスポットのすぐ近くだと 1 歩で音量が跳ぶので、
  幅は最低 `music_spot_gain_min_span_m`(30 m)まで広げる
- 遠い所で鳴り始めると 10 m あたりの差は小さくなる(90 分の散歩で 300 m 先なら約 0.7 dB)。
  気づける下限(1 dB 前後)を割るが、**利用者判断で問題なしとした**(2026-09-11)

散歩のあとの経路図に、スポットの位置を ♪ で出すようにした(答え合わせのため)。
スポットに近づかなかった散歩でも図からはみ出さないよう、図の範囲にも含める。

### スポットは鳴り始めた地点から置く(2026-09-11 利用者判断)

以前は出発時に、出発点のまわりに置いていた。頭の向きが定まるのを待つ間(上限 120 秒)に
60 m 先のスポットを通り過ぎ、**近づく過程が無音になった**
(2026-09-10 の散歩 3: 35 秒後に着き、鳴り始めは 120 秒後)。

いまは**音楽が鳴り始める時に、その地点のまわりに置く**。
置き方(帯の距離・方位の刻み・道に乗せる)は変えていない。

- どこで鳴り始めても、近づく過程が必ず聞こえる
- 鳴り始める前に散歩が終われば、スポットは置かれない(経路図にも出ない)。
  ログには「鳴らさないまま終了」と残す
- 「出発点から 100 m 以内」ではなくなった。出発点からの距離は、待つ間に歩いた分だけ
  延びうる(帰り道は自宅へのビーコンが別に担うので影響しない)

### スポットの近くでピンポイントに感じられるようにする(2026-09-15 利用者依頼)

2026-09-14 の散歩の感想:

> 鳴り始めの音量が小さい時には、1 周回転しても音の変化が感じにくい。
> スポットに近づいた時、最終的にどこにあるか分かりにくく、それに付随して
> スポットの近くに行ったのにゴールした感がない

依頼は「**まずスポットの 5 m 以内で、この角から音が鳴っているなどのピンポイントに
スポットの位置を感じられる体験を**」。

**ログで分かったこと**(`field-logs/field-log-20260914-092222.tsv`・集計は
`scripts/music_near.awk` と `scripts/music_bearing_split.awk`):

| | 実測 |
|---|---|
| GPS の水平精度(近づく間) | **14 m** のまま |
| GPS 上の最接近 | **6 m**(= 5 m 以内には一度も入っていない) |
| 15 m より内側の音量 | **24 秒間 0.90 のまま**(最大に貼り付き、近づいても変わらない) |
| 直線の方位の変化 | 6〜7 m の所を通り過ぎる間も 1 秒に +1〜15°(滑らか) |
| 実際に鳴らした方位の跳び | 00:19:10 に **+51°**、00:19:28 に **+45°** |
| その原因 | 道の向き(スポットへの次の一歩)が **119° → 215°**・**234° → 320°** と切り替わった |

つまり「最終的にどこにあるか分からない」は、(1) 近くで音量が変わらない、
(2) 方位が道の向きの切り替わりで跳ぶ、(3) 近くでも遠くでも鳴り方が同じ、の 3 つが重なっていた。
**GPS の位置の揺れで方位が跳んだのではない**(直線の方位は滑らかだった)。

**やったこと**:

1. **正面に向けた時だけ大きく鳴らす(首を振って探せる)。**
   正面から外れるほど音量を下げ、60° 以上外れたら 12 dB 下げる。
   首を 1 周振ると音量の山がスポットの向きにちょうど 1 つだけでき、真後ろは正面より
   12 dB 小さいので**前後も音量で分かる**(HRTF では前後が伝わらない・docs/03)。
   **頭の向きが定位の基準の時だけ**掛ける(進行方位が基準の間は首を振っても基準が動かず、
   低速の進行方位は跳ぶので音量が暴れるだけになる)
2. **スポットの近くでは道の向きを混ぜない。** 混ぜる比を近さに応じて 0 へ下げる
3. **音量が最大になる距離を 15 m から 5 m へ**(`music_spot_reference_distance_m`)。
   ピンポイントの範囲に入るまで大きくなり続ける

**効果は 15 m から効き始め、5 m 以内で最大**(`music_spot_pinpoint_start_m` /
`music_spot_pinpoint_full_m`)。GPS の誤差が 14 m あるので、5 m で急に切り替えると
一度も発動しない(実測の最接近は 6 m)。距離に比例して強めるので、6 m でも 9 割効く。

| 距離 | 近さ | 60° 以上外した時の下げ幅 | 道の向きを混ぜる比 |
|---|---|---|---|
| 15 m 以上 | 0 | 0 dB(従来どおり) | 0.5(従来どおり) |
| 10 m | 0.5 | 6 dB | 0.25 |
| 6 m | 0.9 | 10.8 dB | 0.05 |
| 5 m 以内 | 1 | **12 dB** | **0** |

音量の最大を 5 m へ移したので、近づく間の 10 m あたりの差はわずかに小さくなる
(90 m で鳴り始めた散歩で 2.8 → 2.5 dB)。

**採らなかったこと**:

- **遠くを残響多め・高域控えめにして、近くで乾いた明るい音にする**(docs/08 柱 1 の構想)。
  近さの手がかりとしては強いが、**遠くの音がぼやけて、「鳴り始めの小さい音では回転しても
  変化が分からない」をさらに悪くする**。今回は見送り
- **スポットのごく近く(数 m)で方位を固定する。** GPS 上 6 m より近づいた記録が無く、
  必要かどうか分からない。次の散歩で 5 m 以内の方位の揺れを見てから決める

**検証**(Codex・`codex-exchange/music-pinpoint-check.reply.md`): 受け入れ条件 P1〜P10 すべて満たす、
**実機投入可**。次の散歩で確かめること(優先順):

1. **数 m の所で直線の方位そのものが正しいか。** GPS の誤差 14 m に対してスポットまで数 m では、
   方位が滑らかでも向きごと誤っている可能性がある(ログの 近さ= が 1 に近い区間で、
   首を振った時の山の向きがスポットの実際の向きと合っていたか)
2. **定位の基準が頭部 ↔ 進行方位で切り替わる瞬間に、音量が最大 12 dB 一度に跳ぶ。**
   正面の強調は頭部の時だけ掛けるため。通常の更新(1 回あたり 1 dB 弱)より大きい段
3. 音量を頭方位の受信ごとに書き換える時のジッパー音(判定不能・実機でしか分からない)

Codex の挙げた「Controller から音声出力・ログまでの統合テスト」は**見送った**。
Controller(App 層)を検査するテストは現状 1 本も無く、音声出力と位置情報を差し替えられる
作りへの改修が要る(今回の範囲を超える)。配線は Codex が静的に確認している(P8・P9)。

**判断待ち**: スポットを**曲がり角(交差点)に置く**か。
依頼の「この角から鳴っている」は、目に見える目印があって初めて成り立つ。
いまのスポットは道の途中の任意の点で、近くに行っても目で見て「ここだ」と言える物が無い。
GPS の誤差(14 m)があっても、見えている角の方から鳴っていれば、人は音をその角に結び付ける
(視覚が音の位置を引き寄せる)。**置き方の仕様を変えるので利用者の判断**。

### 向きで音量を割り振る / 基準を切り替えない(2026-09-18 の 2 回目の散歩)

5 分・331 m・**最接近 2 m**。前回の手当て(後方の高域を落とす・個人化 HRTF)を入れて歩いた。

利用者の感想:

> **前後は 1(答えられる)も 2(後ろから聞こえる)も成り立たず、左右に顔を振らないと分からない。**
> 音楽が不自然になることはなかった。
> **途中で音楽の向きの変化が離散的になったタイミングがあった。**
> 左右のイヤホンの**音量の合計がほぼ一定**なので、左右に偏った時だけはっきり分かる。
> 合計を一定にしなくてよいのでは。実際の聞こえ方(耳の形・注意の向き)で割り振ってよい。

#### 離散的になった原因 — 基準の切り替え

ログ(`scripts/music_reference_switch.awk`)で特定できた。**定位の基準が 16 回切り替わっていた。**

| 時刻 | 起きたこと |
|---|---|
| 01:13:01 | 検疫が退避 → 基準が **頭部 → 進行**。相対方位が **+71° 跳んだ** |
| 01:13:01〜01:13:54 | **53 秒間、進行方位が基準**。首を振っても音が動かず、course の更新に合わせて階段状に動く |
| 01:13:22 | 基準が **なし** → 音が**中央へ飛ぶ** |
| 01:13:54 | 頭部へ復帰 |

前回の散歩は頭部の採用 100%、今回は 57%。**首を振って探すほど、検疫は退避を出しやすくなる**
(取り付けのずれの学習が course との差で成り立っているため・docs/13)。
**探すために首を振る**というこの体験と、検疫の前提が噛み合っていない。

→ **音楽スポットでは検疫の判断を無視する**(`head_mount.music_ignores_quarantine`)。
鮮度(更新が止まったら使わない)と取り付けのずれの学習は守る。
磁気の乱れで向きがずれる危険は残るが、**基準が飛ぶ方が体験を壊す**という判断(利用者)。
ログでは「頭部(検疫外)」と出る。

#### 向きで音量を割り振る

HRTF は左右の差で向きを伝えるが、**左右を足した音量はほぼ一定**になる。
そのため「左右に偏った時だけ分かる」状態だった。

→ 正面を大きく、真後ろを小さくする(`music_spot_directivity_depth_db` = 9 dB)。
形は余弦(頭の影の効き方に近い)で、**距離によらず**掛かる。

| 向き | 音量 |
|---|---|
| 正面 | 0 dB |
| 真横 | −4.5 dB |
| 真後ろ | **−9 dB** |

**代償**: 音量は距離も表しているので、向きと距離が混ざる。
深くするほど前後は分かるが、近い / 遠いが分かりにくくなる
(距離の幅は 21 dB。その半分を超えないことをテストで固定した)。

### 前後を音色で補助する(2026-09-18 利用者依頼)

2026-09-18 の散歩(12 分・988 m・GPS 精度 平均 6 m・頭部固定の採用 91%)の感想:

> **音楽の前後が弱い。前で鳴っているか後ろで鳴っているか分からない。**

実測: スポットへ最接近 12 m。近づく間の相対方位は **+84°〜+169°**(ほぼ真横から後ろ)で、
**正面に置かれた時間がほとんど無い**。前後を比べる材料自体が少ない散歩だった。

**やったこと**: 後ろから鳴っている時だけ**高域を落とす**(真横から真後ろへ滑らかに増やし、
真後ろで最大 `music_spot_rear_shelf_depth_db`(6 dB)。`music_spot_rear_shelf_hz`(4 kHz)以上)。
現実でも後ろの音は頭と耳介に遮られて高域が減る。それを**弱く**模す。

| | |
|---|---|
| 正面〜真横(90°) | 何もしない |
| 真横と真後ろの中間(135°) | −3 dB |
| 真後ろ(180°) | **−6 dB** |

- **強いローパスにはしない。** HRTF が前後の判断に使う高域まで削ってしまう(2026-09-18 合議)
- **音量は変えない。** 音量は距離を表す約束なので、前後で下げると距離と競合する
- 画面の「後ろの音を暗くする」で切れる。**同じ散歩の中で聴き比べる**ため

**採らなかった案**(いずれも 2026-09-18 の合議):

| 案 | 採らない理由 |
|---|---|
| iOS の「スマホの方向から鳴らす」機能を使う | **スマホを頭に固定しているので意味を失う**(端末と頭が一緒に回る)。利用者が挙げた `setIntendedSpatialExperience` は visionOS 向けで iOS には無い |
| 後ろで音量を大きく下げる | 「通り過ぎたら後ろから鳴る」を失う。音量 = 距離とも競合する |
| 前後で残響を変える | 距離や遮蔽物の違いにも聞こえ、「後ろ」と一意に結び付かない |
| わずかな音程差 | 学習する記号にはなるが、音楽そのものを変えてしまう |
| PHASE への移行 | 移行だけで前後が解決する保証が無い |
| `outputType = .headphones` の明示 | いま `.HRTFHQ` を明示しており、これで前後が改善する根拠が無い |

### 個人化 HRTF を使う(2026-09-18 利用者依頼)

**利用者が設定で作った「個人用の空間オーディオ」の形(耳と頭の形)を、こちらの音にも使う。**
汎用 HRTF で前後が伝わらないのは、耳介の形が人それぞれだから。個人の形を使えば、
前後と上下の手がかりが効く見込みがある。

**やったことは権利情報を 1 つ足すだけ**(`Support/OtoSanpo.entitlements`・project.yml で生成):

```
com.apple.developer.spatial-audio.profile-access
```

- **コードの呼び出しは要らない。** この権利情報があると `AVAudioEngine` の定位に自動で適用される
  (Apple の資料「Personalizing spatial audio in your app」。AVAudioEngine / AUSpatialMixer /
  PHASE の 3 つが対象)
- **iOS 18 以降**。利用者側で「設定 > (AirPods)> 個人用の空間オーディオ」を作っていて、
  対応する AirPods を使っている必要がある。作っていなければ従来どおり汎用 HRTF
- 署名に入ったことは `scripts/check_key.sh` が確かめる。
  **入っていなくても音は鳴る**(黙って汎用 HRTF に戻る)ので、検査で押さえる

**AirPods のヘッドトラッキングは入れない。** それは別の権利情報
(`com.apple.developer.coremotion.head-pose` + `isListenerHeadTrackingEnabled`)で、
**この装置では二重に回る** — 頭の向きはスマホの `CMMotionManager` から取っているため。
`DistributionHygieneTests` が「入っていないこと」を検査する。

**効果は未確認。** 個人プロファイルの有無で聞こえ方が変わるかは実機でしか分からない。

**評価は 3 つに分ける**(2026-09-18 合議): 「前後を答えられたか」「後ろから聞こえたか」
「音楽が不自然になったか」。**暗い音を後ろと答えられても、後方定位が成立した扱いにはしない。**

### 音の向きの基準を画面から選べるようにした(2026-09-18 利用者依頼)

音楽スポットを選んだ時だけ、「進む向き」と「頭の向き(スマホを頭に固定)」を画面で選べる
(→ Core の `OrientationMode`)。**既定は進む向き。**

**実験の値とは混ぜない。** `head_mount.enabled` は頭部固定のほかに有効性パルス・実験用の音色・
詳しいログも切り替えるので、画面の選択が決めるのは**定位の基準をどこから取るか**だけにした。
画面で頭部固定を選んでも、パルスや実験音色は有効にならない
(`OrientationModeTests` が番人)。

使うかどうかは**出発時に決める**(歩き出してから変えない)。途中で設定を触っても、
鳴り方が散歩の途中で変わらないようにするため。

### 直線と道の間から鳴らす(2026-09-10 利用者依頼 → **2026-09-18 に取りやめ**)

> **いまは混ぜていない**(`music_spot_route_blend` = 0)。
> **「最短経路との足し算はなくし、スポットの方向だけで鳴らす」**(2026-09-18 利用者判断)。
> 混ぜていた間、方位の跳びは**すべて道の向きの切り替わりが原因**だった
> (2026-09-14 の散歩で 1 秒に 45〜51°。直線の方位は同じ間 15° 以内で滑らか)。
> スポットの近くでは既に混ぜない作りにしていたが、遠くでも混ぜないことにした。
> 値を戻せば元の挙動に戻る(経路の場は比が 0 なら解かない)。以下は当時の設計。

直線の向きだけだと、建物の向こうから鳴っているのに「そちらへ行けない」ことになる。
道をたどる向きだけだと、曲がり角のたびに音が飛んで**スポットに居る感じ**が薄れる。

**間を取る**(`music_spot_route_blend` = 0.5)。
「あちらに在って、こう行けば着く」が同時に伝わる。

- スポットへの経路の場を**背景で解く**(自宅への場とは別に 1 つ)。
  できるまでは直線の向きだけで鳴らすので、音楽は待たされない
- 角度は円周上の量なので、**線形に混ぜてはいけない**
  (350° と 10° の中間は 0° であって 180° ではない)。単位ベクトルで混ぜる

### 音の経路(踏んだ落とし穴)

`AVAudioEnvironmentNode` は**モノラル入力にしか効かない**ので、
`musicPlayer(音源の形式)→ musicMixer(モノラルへ落とす)→ environment` と繋ぐ。

**定位を設定するのは `musicMixer` の側。** `AVAudioMixing` の `position` /
`renderingAlgorithm` が効くのは「その接続先が持つ入力バス」で、
上流の `musicPlayer` に設定しても**定位は付かない**(2026-09-09 の検証で判明)。

エンジンは AirPods の抜き差しで止まり、**接続が全部壊れる**。音源の形式を覚えて
繋ぎ直さないと「音楽だけが黙って鳴らなくなる」。再生位置は失われるので
**勝手に鳴らし直さず**、中断したことを記録する(「一度だけ」の約束を守る)。

**畳まないと決めた理由**: 点の earcon は「後ろから鳴らない」ために前へ畳んでいる
(docs/03)。音楽は通り過ぎれば後ろにあるのが自然で、畳むと
**通り過ぎたことが分からなくなる**。連続音では前後が体験の一部になる。
