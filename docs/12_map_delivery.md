# 12. 地図の配り方 — 自動取得の設計(2026-08-28 計画)

テスターごとに経路データを手で渡すのをやめ、**散歩を開始したら半径 5 km 圏の地図を
アプリが自分で取ってくる**形にできるか。

動機は配布の手間。iOS はファイルアプリ経由、Android は `Android/data/` へ置く必要があり、
**Android のテスターは実際に置けなかった**(2026-08-28。→ [docs/10](10_android.md))。

## これは通信の有無を変える判断である

**技術の話の前に、約束が 3 つ変わる。**

| いまの約束 | どこに書いてあるか | 自動取得後 |
|---|---|---|
| アプリは通信を一切しない | README / [docs/09](09_tester_guide.md) | **できなくなる** |
| データを収集していません | App Store Connect の「App のプライバシー」 | **申告の変更が要る** |
| 記録は端末から出ない | docs/09・テスターへの説明 | **維持できる**(下記) |

**維持できる線はここ:**

> 歩いた経路・自宅・フィールドログは一切送らない。
> 送るのは**地図を取るためのタイル番号だけ**。

**守れなくなる線:**

> 通信を一切しない。

この差をテスターに説明できるかが、採否の分かれ目になる。

## 決めるべきこと 3 つ

### 1. どの粒度で位置を送るか

| 方式 | 送る情報 | 相手に分かる粒度 |
|---|---|---|
| 座標をそのまま | `35.1851,136.8998` | **数 m。実質、自宅が渡る** |
| タイル番号 | `(1758, 6845)` | タイルの大きさ(数 km) |
| 都市を選ばせる | 「名古屋市」 | 都市 |

**座標をそのまま送るのは論外。** タイル番号にする。

ただし注意: **5 km 圏を覆う複数タイルを取ると、その交差から中心が絞れる。**
9 枚取れば中心は真ん中のタイルだと分かる。**粒度はタイル 1 枚ぶんに落ちるだけ**で、
「タイルにしたから安全」ではない。

隠しきるには「必要より広く取る」「ダミーを混ぜる」といった手が要るが、
通信量と釣り合うかは別の判断。

### 2. どこから取るか

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **a. 事前生成したタイルを静的配信** | **安い・速い・規約が明快。** `MapBuild` がそのまま使える | 全国ぶん **1.4〜2 GB** を置く。更新は手動(月次程度) |
| b. Overpass API を直接叩く | 常に最新・置き場が要らない | **公開 API への依存。** レート制限があり、応答は数秒〜数十秒。規約上、常用するなら自前サーバを立てるべき |
| c. 自前の変換サーバ | 好きな形で返せる | サーバの運用が発生する |

**a を勧める。** 散歩の開始時に Overpass の応答を待つのは体験として持たない。
静的ファイルなら、失敗しても原因が分かりやすい。

全国 1.4〜2 GB は [docs/04](04_route_gesture_privacy.md) の実測。
静的配信なので置き場は安く済む。

### 3. いつ取るか

5 km 圏は **2.1 MB**(実測)。モバイル回線で 3〜10 秒。

| 案 | 体験 |
|---|---|
| 開始時に取り、完了まで待つ | 押してから数秒〜十数秒待つ。**圏外だと始められない** |
| **開始時に取りつつ、届くまではグリッドのみで動く** | すぐ歩き出せる。最初の数分だけ提案の質が落ちる |
| 事前に取る(Wi-Fi 時・前日) | 待たない。ただし「いつ取るか」の仕組みが要る |

**2 番目を勧める。** 「地図が無ければグリッドのみで動く」経路は既にあるので、
**そこに乗せるだけ**で済む。届いたら差し替える。

## 設計の骨格

### タイル

- **緯度経度の等分割**。投影は要らない(`z/x/y` のような仕組みは過剰)
- 0.05° 角 = 約 5.6 km × 4.6 km(35°N)。**5 km 圏は 3×3 = 9 枚**で覆える
- タイル番号は整数 2 つ。`floor(lat / 0.05)`, `floor(lon / 0.05)`

サイズの見積もり(実測からの外挿。密度は名古屋 31 KB/km² 〜 金沢 7.8 KB/km²):

| | 面積 | サイズ |
|---|---|---|
| タイル 1 枚 | 約 26 km² | **200〜800 KB** |
| 5 km 圏(9 枚) | 約 230 km² | **1.8〜7 MB** |

既存の 5 km 地図 2.1 MB と整合する。

### 作るもの

| 層 | 中身 |
|---|---|
| Core | `MapTile`(座標 → 番号、圏内の列挙)、**複数タイルから `WalkMap` を組む** |
| Services | 取得(`URLSession`)・キャッシュ・失敗時の退避 |
| App | 取得中の表示、圏外時の振る舞い |
| PC 側 | 全国ぶんのタイルを生成して配信先へ上げるスクリプト |

**変えなくてよいもの**: `WalkGraph` / `RouteField` / `ZoneMap` / 提案・誘導の一式。
タイルを結合して `WalkMap` を作れば、下流はそのまま動く。

### キャッシュ

- 一度取ったタイルは残す。**生活圏は数回の散歩で揃う**
- 容量の上限と追い出し(古い順)。全国を溜め込ませない
- **更新**: OSM は変わる。タイルに生成日を持たせ、古ければ取り直す(90 日など)

### 失敗したとき

圏外・配信先の障害・容量不足。**いずれもグリッドのみで動く**(既存の経路)。
黙って劣化させず、画面に「地図: 取得中」「地図: 取得できず」と出す。

## 先に比べるべき代案

**自動取得は、配布の手間を消すための手段でしかない。** 他の解と並べる。

| 案 | テスターの手間 | 通信 | 実装 |
|---|---|---|---|
| APK / IPA に同梱 | **ゼロ** | なし | **Android は実装済み** |
| **アプリ内で都市を選んで落とす** | 1 回だけ選ぶ | あり(**都市名だけ**) | 中(タイル化が要らない) |
| 自動取得 | ゼロ | あり(タイル番号) | 大 |

**「アプリ内で都市を選ぶ」が、手間と通信の釣り合いが良い。**

- **位置を送らない。** 送るのは利用者が自分で選んだ都市名
- タイル化が要らず、**いまある 34 都市のファイルをそのまま落とせる**
- 「データを収集していません」の申告を**変えずに済む可能性がある**
  (利用者が明示的に選んだ都市名だけなので。**要確認**)

自動取得の利点は「何も選ばなくてよい」ことだけで、その代わりに
**位置の送信・タイル化・全国の配信**を抱える。

## 段取り

| 段 | 中身 | 確かめ方 |
|---|---|---|
| 0 | **都市を選んで落とす** | 位置を送らない。既存の 34 ファイルをそのまま使える |
| 1 | タイル化(Core + MapBuild) | 机上。既存の地図と同じ結果になるか |
| 2 | 取得とキャッシュ | 机上 + 実機で 1 回 |
| 3 | 自動取得の配線 | 散歩 1 回 |

**段 0 だけで目的の 8 割は達成できる見込み。** 段 1 以降へ進むかは、段 0 を配ってから決める。
