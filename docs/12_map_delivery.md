# 12. 地図の配り方 — 自動取得の設計(2026-08-28 計画)

テスターごとに経路データを手で渡すのをやめ、**散歩を開始したら半径 5 km 圏の地図を
アプリが自分で取ってくる**形にできるか。

動機は配布の手間。iOS はファイルアプリ経由、Android は `Android/data/` へ置く必要があり、
**Android のテスターは実際に置けなかった**(2026-08-28。→ [docs/10](10_android.md))。

## これは通信の有無を変える判断である

| 記録は端末から出ない | docs/09・テスターへの説明 | **維持している** |

**書き換えた 4 箇所**(2026-08-28):

| 場所 | 何を直したか |
|---|---|
| `README.md` | 外へ出るのは地図の取得だけ、送るのは区画の番号のみ |
| `docs/09`(テスター向け) | 「通信を一切しない」→「**ボタンを押した時だけ**通信する」 |
| `docs/01`(原則) | 「送信ゼロ」の見直しを決定として記録 |
| `project.yml` の位置情報の説明文 | **権限ダイアログに出る文言。** 区画の番号を送ることを明記 |

**App Store Connect の「App のプライバシー」は要確認。**
送るのは区画の番号(端末や人に紐づかない)で、収集も保存もしていないため
「データを収集していません」のままで通る可能性が高いが、**未確認**。
次に配信する前に見直すこと。

**維持できる線はここ:**

> 歩いた経路・自宅・フィールドログは一切送らない。
> 送るのは**地図を取るためのタイル番号だけ**。

**守れなくなる線:**

> 通信を一切しない。

この差をテスターに説明できるかが、採否の分かれ目になる。

## 決めるべきこと 3 つ

### 1. どの粒度で位置を送るか

| 方式 | 送る情報 | 相手に分かる粒度 |
|---|---|---|
| 座標をそのまま | `35.1851,136.8998` | **数 m。実質、自宅が渡る** |
| タイル番号 | `(1758, 6845)` | タイルの大きさ(数 km) |
| 都市を選ばせる | 「名古屋市」 | 都市 |

**座標をそのまま送るのは論外。** タイル番号にする。

ただし注意: **5 km 圏を覆う複数タイルを取ると、その交差から中心が絞れる。**
9 枚取れば中心は真ん中のタイルだと分かる。**粒度はタイル 1 枚ぶんに落ちるだけ**で、
「タイルにしたから安全」ではない。

隠しきるには「必要より広く取る」「ダミーを混ぜる」といった手が要るが、
通信量と釣り合うかは別の判断。

### 2. どこから取るか

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **a. 事前生成したタイルを静的配信** | **安い・速い・規約が明快。** `MapBuild` がそのまま使える | 全国ぶん **1.4〜2 GB** を置く。更新は手動(月次程度) |
| b. Overpass API を直接叩く | 常に最新・置き場が要らない | **公開 API への依存。** レート制限があり、応答は数秒〜数十秒。規約上、常用するなら自前サーバを立てるべき |
| c. 自前の変換サーバ | 好きな形で返せる | サーバの運用が発生する |

**a を勧める。** 散歩の開始時に Overpass の応答を待つのは体験として持たない。
静的ファイルなら、失敗しても原因が分かりやすい。

全国 1.4〜2 GB は [docs/04](04_route_gesture_privacy.md) の実測。
静的配信なので置き場は安く済む。

### 3. いつ取るか

5 km 圏は **2.1 MB**(実測)。モバイル回線で 3〜10 秒。

| 案 | 体験 |
|---|---|
| 開始時に取り、完了まで待つ | 押してから数秒〜十数秒待つ。**圏外だと始められない** |
| **開始時に取りつつ、届くまではグリッドのみで動く** | すぐ歩き出せる。最初の数分だけ提案の質が落ちる |
| 事前に取る(Wi-Fi 時・前日) | 待たない。ただし「いつ取るか」の仕組みが要る |

**2 番目を勧める。** 「地図が無ければグリッドのみで動く」経路は既にあるので、
**そこに乗せるだけ**で済む。届いたら差し替える。

## 設計の骨格

### タイル

- **緯度経度の等分割**。投影は要らない(`z/x/y` のような仕組みは過剰)
- 0.05° 角 = 約 5.6 km × 4.6 km(35°N)。**5 km 圏は 3×3 = 9 枚**で覆える
- タイル番号は整数 2 つ。`floor(lat / 0.05)`, `floor(lon / 0.05)`

サイズの見積もり(実測からの外挿。密度は名古屋 31 KB/km² 〜 金沢 7.8 KB/km²):

| | 面積 | サイズ |
|---|---|---|
| タイル 1 枚 | 約 26 km² | **200〜800 KB** |
| 5 km 圏(9 枚) | 約 230 km² | **1.8〜7 MB** |

既存の 5 km 地図 2.1 MB と整合する。

### 作るもの

| 層 | 中身 |
|---|---|
| Core | `MapTile`(座標 → 番号、圏内の列挙)、**複数タイルから `WalkMap` を組む** |
| Services | 取得(`URLSession`)・キャッシュ・失敗時の退避 |
| App | 取得中の表示、圏外時の振る舞い |
| PC 側 | 全国ぶんのタイルを生成して配信先へ上げるスクリプト |

**変えなくてよいもの**: `WalkGraph` / `RouteField` / `ZoneMap` / 提案・誘導の一式。
タイルを結合して `WalkMap` を作れば、下流はそのまま動く。

### キャッシュ

- 一度取ったタイルは残す。**生活圏は数回の散歩で揃う**
- 容量の上限と追い出し(古い順)。全国を溜め込ませない
- **更新**: OSM は変わる。タイルに生成日を持たせ、古ければ取り直す(90 日など)

### 失敗したとき

圏外・配信先の障害・容量不足。**いずれもグリッドのみで動く**(既存の経路)。
黙って劣化させず、画面に「地図: 取得中」「地図: 取得できず」と出す。

## 先に比べるべき代案

**自動取得は、配布の手間を消すための手段でしかない。** 他の解と並べる。

| 案 | テスターの手間 | 通信 | 実装 |
|---|---|---|---|
| APK / IPA に同梱 | **ゼロ** | なし | **Android は実装済み** |
| **アプリ内で都市を選んで落とす** | 1 回だけ選ぶ | あり(**都市名だけ**) | 中(タイル化が要らない) |
| 自動取得 | ゼロ | あり(タイル番号) | 大 |

**「アプリ内で都市を選ぶ」が、手間と通信の釣り合いが良い。**

- **位置を送らない。** 送るのは利用者が自分で選んだ都市名
- タイル化が要らず、**いまある 34 都市のファイルをそのまま落とせる**
- 「データを収集していません」の申告を**変えずに済む可能性がある**
  (利用者が明示的に選んだ都市名だけなので。**要確認**)

自動取得の利点は「何も選ばなくてよい」ことだけで、その代わりに
**位置の送信・タイル化・全国の配信**を抱える。

## 段取り

| 段 | 中身 | 確かめ方 |
|---|---|---|
| 0 | **都市を選んで落とす** | 位置を送らない。既存の 34 ファイルをそのまま使える |
| 1 | タイル化(Core + MapBuild) | 机上。既存の地図と同じ結果になるか |
| 2 | 取得とキャッシュ | 机上 + 実機で 1 回 |
| 3 | 自動取得の配線 | 散歩 1 回 |

**段 0 だけで目的の 8 割は達成できる見込み。** 段 1 以降へ進むかは、段 0 を配ってから決める。

## 実装した形(2026-08-28・`feature/map-download`)

**タイル方式。** 「この辺りの地図を取得」を押すと、現在地の周り(散歩の 5 km 圏)の
タイルを落とす。

> 最初は「都市を選んで落とす」(位置を送らない)で作ったが、**同日中に置き換えた**。
> 20 km 円の都市ファイルは「手で 1 ファイル渡す」前提の分割で、
> ダウンロードなら必要な範囲だけ取ればよい(利用者判断・2026-08-28)。
> 40 MB の都市ファイルが数 MB の取得で済み、都市の円から漏れる地域も無くなる。

### タイル

- **緯度経度の等分割**(`tile_size_deg` = 0.05° ≈ 5.6 × 4.6 km)。投影は使わない
- タイル番号 = floor(緯度 / 角), floor(経度 / 角)。ファイル名 `t{y}_{x}.json`
- **1 枚 = 1 つの `WalkMap`**。既存の読み込み・再生ツールがそのまま読める
- 5 km 圏は最大 3×3 = 9 枚。実測(四国)で平均 157 KB / 最大 1.6 MB(松山中心)
- **way は重心が属するタイルにだけ入る**(重複を作らない)。境目の節点は
  両側のタイルに同じ座標で入り、端末側の結合(`MapTiles.assemble`)で 1 つに畳まれる。
  **畳まなければタイルの縁でグラフが切れ、帰路の経路の場が縁で止まる**(テストで固定)

### 送るもの / 送らないもの

| | |
|---|---|
| 送る | **取得する区画(タイル)の番号。粒度は約 5 km 角** |
| 送らない | **正確な位置・歩いた経路・自宅・フィールドログ** |

都市名方式(位置を送らない)から、**タイル番号(約 5 km 角の粒度)を送る**方式へ
変わっている。これは利用者判断(2026-08-28)。画面にもこの文言で明示する。
取得は**ボタンを押した時だけ**(散歩開始時の自動取得は判断待ち)。

### 手で入れた地図と衝突させない

20 km 円のファイルを配っていた時期があり、**それを持つ端末で取得しても壊れない**こと:

- タイルは **`Documents/map-tiles/` に置く**。`otosanpo-map.json` は**触らない**
- どちらを読むかは `MapSource.choose`:
  **タイルが勝つのは「タイルは現在地を覆い、手動の地図は覆わない」時だけ**
  (旅行先・引っ越しがこれ)。それ以外で手動があれば手動 —
  人が置いたものを黙って差し替えないし、既存テスターの挙動が変わらない
- 選び直すのは起動時と散歩の開始時(位置が確定した時点)と取得の直後
- 画面の「地図:」行に出どころが出る(`半径20km・…` / `タイル 9 枚・…`)

### 配信先(Cloudflare R2)

**全国ぶんは 17,173 枚 / 2.4 GB**(2026-08-28 に 8 地方から生成・実測)。
R2 の無料枠は 10 GB、**下り転送も無料**(生成前の使用は 147.85 MB / $0.00)。

| 地方 | 新規 | 追記(境界の重なり) | 書いた量 |
|---|---|---|---|
| 中部 | 3,013 | 0 | 480 MB |
| 関東 | 1,379 | 110 | 435 MB |
| 九州(沖縄含む) | 2,364 | 7 | 374 MB |
| 東北 | 2,896 | 108 | 297 MB |
| 関西 | 1,374 | 106 | 296 MB |
| 中国 | 1,491 | 14 | 224 MB |
| 北海道 | 3,726 | 0 | 148 MB |
| 四国 | 930 | — | 144 MB |

重複除去の検証: 四国を 2 度流したところ**全 930 枚が「追記」扱いで中身は不変**
(松山中心のタイルが節点 42,000 / 道 9,432 のまま)。地方の境界の重なりも
追記(計 345 枚)として正しく畳まれた。

```
<公開 URL>/meta.json        タイル角と生成日。**タイル角は配信側が宣言する**
<公開 URL>/t{y}_{x}.json    タイル本体。404 = その区画に道のデータが無い(海など)
```

一覧ファイルは**無い**。タイル名は座標から計算できるので、404 を「データ無し」として
扱えば足りる(1 万数千件の索引を持つ必要がない)。

作る・上げる:

```bash
scripts/build_tiles.sh
```

```bash
scripts/upload_tiles.sh <バケット名>
```

**アップロードは人が実行する**(認証情報が要るため。実機への配備と同じ方針)。
バケットは**公開アクセスを有効**にすること(アプリは認証を持たない)。

### 転送は rclone で行う(2026-08-29 に置き換え)

最初は `npx wrangler r2 object put` を 1 ファイルずつ呼んでいた。**2 つとも駄目だった。**

1. **npx が wrangler のインストール確認を対話で聞き、出力をログへ流していたため
   答えられず、1 件目で 12 時間止まった。** 経過時間 12:13 に対し CPU 時間は 1.36 秒で、
   「遅い」のではなく**何もしていなかった**
2. 直しても **1 ファイルごとに Node を起動する**ので、17,173 件では数時間〜十数時間かかる

rclone は S3 API を直に叩き、**並列**で送り、**中断しても差分だけ**送り直せる。

**前段に疎通の確認を必ず置く。** 一晩を溶かした原因は
「始まってすらいないことに気づけなかった」ことなので、
権限が無ければ**数秒で・理由を示して**止まるようにした。

R2 の API トークンは **Object Read & Write** が要る。
**読みも要る** — rclone は差分を見るために HeadObject するので、
書き込みだけのトークンでは 403 で止まる。

### 設定

`config/parameters.json` の `map_download`:

- `base_url` — **空なら取得の機能を画面に出さない**(通信しない状態に戻せる)
- `tile_size_deg` — **生成側**が使う。アプリは配信先の `meta.json` の値を使う
  (配信データの分割はデータと一緒に宣言されるべきで、食い違えば配信側が正)

### 作ったもの

| 層 | 中身 |
|---|---|
| Core | `MapTiles`(番号・取得範囲・結合)/ `MapSource`(どの地図で歩くか) |
| Services | `TileStore`(置き場)/ `MapDownloader`(取得)。**唯一、外へ出る通信** |
| App | 「この辺りの地図を取得(5 km 圏)」ボタンと進捗 |
| PC 側 | MapBuild の `--tiles` モード / `scripts/build_tiles.sh` / `scripts/upload_tiles.sh` |

地方データは境界で重なる(Geofabrik は境界をまたぐ道を両方に入れる)ので、
生成は既にあるタイルへ**座標列の一致で重複を除いて追記**する。

### 未確認

- **実機で試していない。** `base_url` が未設定のため
- 全国ぶんの生成・配信は初回のみ。**OSM の更新への追随は手動**(作り直して上げ直す)
- 落とした地図は**次の散歩から効く**。散歩中の差し替えは想定していない
- タイルを溜め続けた端末の上限(容量の掃除)は未実装。1 回の取得は数 MB なので
  当面は問題にならない見込み

## 決まったこと(2026-08-28・利用者判断)

| 項目 | 決定 |
|---|---|
| 通信を入れるか | **入れる**(タイルの取得) |
| 位置の粒度 | **タイル番号(約 5 km 角)**。座標は送らない |
| 配信先 | **Cloudflare R2**(静的配信・無料枠) |
| ファイルの分割 | **タイル**。20 km 円は手動配布の前提だったので、配信では使わない |

## 散歩開始時の自動取得(2026-08-29 決定・実装済み)

**開始時に足りない分だけ裏で取得し、届くまではいまの地図(無ければグリッド)で歩く。**
自宅スタートが基本で、操作を一つ減らせるため(利用者判断)。

- **揃っていれば通信しない。** いつもの場所の散歩は 2 回目から通信ゼロ
- **「データ無し」(404)は印を残し、自動取得では取りに行かない。**
  海沿いの自宅では 5 km 圏の何枚かが恒久的にデータ無しで、
  記録しないと散歩のたびに同じ 404 への通信が走る
- **ボタンからの取得は印を無視してもう一度試す。** 配信が後から増えた場合に
  人の操作で拾い直せるように
- 取得できたら経路の場も作り直す(自動取得は開始直後に走るので、
  放置すると今回の散歩に効かない)
- 失敗しても散歩は止めない(グリッドのみで動く既存の経路)

### 読み込みは自宅・現在地の周りだけ

取得のたびにタイルは溜まる。**全部を結合すると旅行先で取った端末ほど地図が肥大し、
散歩の開始時に作る経路の場が重くなる**(57 万節点で構築 5.1 秒・メモリ 241 MB。docs/04)。
`MapTiles.nearby` で基準点(自宅・現在地)の 5 km 圏に絞って読む。
**ディスク上のタイルは消さない**(消すかどうかは判断待ち 5)。
